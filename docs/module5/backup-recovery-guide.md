# Инструкция по резервному копированию и восстановлению базы данных `rent`

## 1. Общие сведения о системе
* **СУБД:** PostgreSQL 18 (порт `5432`, хост `localhost`).
* **Имя рабочей базы данных:** `rent`.
* **Системный пользователь БД:** `postgres`.
* **Пользователь ОС, от имени которого работает расписание:** `ваш_пользователь`.
* **Утилиты резервного копирования:** `pg_dump` / `pg_restore` (сжатый бинарный формат `-Fc`) и `rclone` (синхронизация с облаком Google Drive или любым другим).

---

## 2. Целевые показатели надёжности (RPO и RTO)

| Метрика | Значение | Обоснование для проекта |
| :--- | :--- | :--- |
| **RPO** *(Recovery Point Objective — допустимая потеря данных)* | **24 часа** | Резервное копирование выполняется один раз в сутки (в `02:00`). Проект представляет собой систему учёта долгосрочной аренды недвижимости: новые договоры, платежи и показания счётчиков вносятся нерегулярно, а операции за последние сутки при необходимости легко восстанавливаются по банковским выпискам и бумажным актам. |
| **RTO** *(Recovery Time Objective — целевое время восстановления)* | **30 минут** | Текущий объём дампа базы данных составляет менее 1 МБ (в перспективе роста — до сотен мегабайт). Скачивание архива из Google Drive и разворачивание БД через `pg_restore` занимает 1–3 минуты; остальное время заложено на диагностику сбоя, пересоздание БД и проверку целостности таблиц администратором. |

## 3. Стратегия резервного копирования и правило 3-2-1

### Обоснование выбора типа копий
Утилита `pg_dump` формирует логический срез данных и не поддерживает блочный инкремент на уровне страниц (как физический `pg_basebackup`). Для баланса между скоростью, объёмом и простотой восстановления выбрана комбинированная схема:
1. **Полная копия (`weekly`):** выполняется 1 раз в неделю (воскресенье, `02:00`). Выгружается вся база данных `rent` целиком, включая статичные справочники, медиа-ссылки и шаблоны документов.
2. **Разностная логическая копия (`daily`):** выполняется ежесуточно (понедельник–суббота, `02:00`). Выгружаются только оперативно изменяемые бизнес-таблицы (`users`, `landlords`, `tenants`, `flats`, `contracts`, `leases`, `lease_amendments`, `payments`, `meters`, `meter_readings`, `requests`, `notifications`), а тяжёлые редко изменяемые таблицы (`contract_templates`, `property_media`) исключаются флагом `-T`. Это снижает нагрузку на диск и ускоряет отправку в облако.

### Реализация упрощённого правила 3-2-1
* **3 копии данных:**
  1. Рабочий кластер PostgreSQL 18 (`/var/lib/postgresql/18/main`).
  2. Локальный архив резервных копий на сервере (`/var/backups/postgres/`).
  3. Удалённая копия в облачном хранилище Google Drive (`cloud:rent_backups/`).
* **2 разных типа носителей:** локальный накопитель сервера и облачное объектное хранилище.
* **1 копия вне основной площадки (off-site):** Google Drive (защита от физического выхода сервера из строя).

## 4. Места хранения, файлы и расписание

### Структура файлов на сервере
* **Скрипт резервного копирования:** `/home/ваш_пользователь/backup_rent.sh`
* **Файл беспарольного доступа к БД:** `/home/ваш_пользователь/.pgpass` *(права `0600`, формат: `localhost:5432:*:postgres:<пароль>`)*
* **Конфигурация облака `rclone`:** `/home/ваш_пользователь/.config/rclone/rclone.conf` *(имя подключения: `cloud`)*
* **Локальные недельные копии:** `/var/backups/postgres/weekly/` *(срок хранения: 28 дней / 4 копии)*
* **Локальные суточные копии:** `/var/backups/postgres/daily/` *(срок хранения: 7 дней)*
* **Журнал выполнения:** `/var/backups/postgres/backup.log`
* **Облачное хранилище:** Google Drive (или другое облако), директории `rent_backups/weekly/` и `rent_backups/daily/`.

### Расписание задач (`crontab -l` от пользователя `egor`)
```cron
# Полный бэкап раз в неделю (каждое воскресенье в 02:00)
0 2 * * 0 /home/ваш_пользователь/backup_rent.sh weekly >> /var/backups/postgres/backup.log 2>&1

# Суточный разностный бэкап (с понедельника по субботу в 02:00)
0 2 * * 1-6 /home/ваш_пользователь/backup_rent.sh daily >> /var/backups/postgres/backup.log 2>&1
```

### Команды для ручного запуска и проверки
* **Запустить полный бэкап вне расписания:**
  ```bash
  /home/ваш_пользователь/backup_rent.sh weekly
  ```
* **Запустить суточный бэкап вне расписания:**
  ```bash
  /home/ваш_пользователь/backup_rent.sh daily
  ```
* **Посмотреть список локальных копий:**
  ```bash
  ls -lh /var/backups/postgres/weekly /var/backups/postgres/daily
  ```
* **Посмотреть список копий в Google Drive:**
  ```bash
  rclone ls cloud:rent_backups
  ```

## 5. Пошаговая процедура аварийного восстановления

### Сценарий А. Полная потеря или повреждение базы данных `rent`
1. **Остановите сервисы/приложения**, обращающиеся к базе данных `rent`, чтобы исключить блокировки при пересоздании БД.
2. **Определите актуальный файл резервной копии:**
   * Если локальный диск доступен, возьмите последний файл из `/var/backups/postgres/weekly/` (а при необходимости наката суточных изменений — также последний файл из `/var/backups/postgres/daily/`).
   * Если локальный диск утерян, скачайте бэкапы из Google Drive (или другого облака) во временную папку:
     ```bash
     mkdir -p /tmp/restore
     rclone copy cloud:rent_backups/ /tmp/restore/
     ```
3. **Удалите повреждённую базу данных и создайте чистую:**
   ```bash
   dropdb -U postgres -h localhost --if-exists rent
   createdb -U postgres -h localhost -E UTF8 rent
   ```
4. **Восстановите полную недельную копию:**
   ```bash
   pg_restore -U postgres -h localhost -d rent -v /var/backups/postgres/weekly/rent_weekly_ГГГГ-ММ-ДД_ЧЧ-ММ.dump
   ```
5. **Если после воскресного бэкапа были суточные изменения (`daily`), накатите актуальные данные из суточного дампа поверх восстановленной базы** *(с флагом `--data-only --disable-triggers`, предварительно очистив оперативные таблицы при необходимости)*:
   ```bash
   pg_restore -U postgres -h localhost -d rent --data-only --disable-triggers -v /var/backups/postgres/daily/rent_daily_ГГГГ-ММ-ДД_ЧЧ-ММ.dump
   ```
6. **Обновите статистику планировщика и проверьте целостность данных:**
   ```bash
   psql -U postgres -h localhost -d rent -c "ANALYZE; SELECT relname AS table_name, n_live_tup AS row_count FROM pg_stat_user_tables ORDER BY relname;"
   ```
7. **Запустите приложения** и убедитесь в корректной работе сервиса.
